# Go framework benchmark on GKE

This directory runs the six Go HTTP stacks (net/http, chi, gin, echo, fiber, fasthttp) on Google Kubernetes Engine in the style of Anton Putra's benchmarks: each app runs as a Deployment with a CPU limit, load generators run as Kubernetes Jobs on a separate node pool, and results come from Prometheus (Google Cloud Managed Service for Prometheus, GMP).

The goal is numbers that can be trusted. Every metric shown in the results or on the dashboard has been checked against a source that does not depend on the load tester. See [Validation](#validation).

**Final results:** [`results/gke-20260925-final/REPORT.md`](../results/gke-20260925-final/REPORT.md). **Method and experiments:** [`docs/benchmark-methodology.md`](../docs/benchmark-methodology.md).

## Architecture

| Component | Where | Details |
|---|---|---|
| Apps | Node pool `apps`: 2 × `n2-standard-4` (Intel Cascade Lake), label `node=general` | One pod per node (pod anti-affinity). CPU request 1500m, limit 2000m, memory 256 MiB, `GOMAXPROCS` from `limits.cpu`. Manifests in `k8s/apps/`. |
| Load testers | Node pool `clients`: 1 × `n2-highcpu-16`, label `node=clients` | 5 pods per framework, 1 CPU each, 128 keep-alive connections per pod. Template `k8s/tester.yaml.tmpl`, image built from `../loadtester`. |
| Metrics | GMP managed collection | `PodMonitoring` scrapes the testers every 5 s (`k8s/base.yaml`). App CPU, memory and throttling come from cAdvisor. |
| Grafana | Node pool `default-pool` (`node=system`) | Dashboard generated by `grafana/dashboard.py`; deployed with `grafana/deploy.sh`. |

The session's egress proxy cannot reach the GKE API server, so `kctl.sh` runs `kubectl` from inside Cloud Build.

## Load model

The tester (`../loadtester`) generates an **open-model** load, like wrk2. Each of its 128 workers owns one connection and sends requests on a fixed schedule, independent of how fast the server answers.

- **Latency** is measured from each request's *scheduled* send time. If the server is slow, the queueing delay is recorded instead of hidden (no coordinated omission).
- **Deadline.** Each request has a deadline of `DEADLINE_MS` (1 s) after its scheduled time, like a user who gives up. When all connections are busy and a request's deadline passes before it can be sent, it is not sent and is counted in `tester_dropped_requests_total`. Requests already in flight are not cancelled, because closing their connections would add reconnect load that real users would not cause.
- **Accounting.** Every scheduled request is recorded exactly once: as a response (by status) or as dropped. This keeps an overloaded run's backlog bounded and stops sending about 1 s after the last stage.
- **One attempt per request.** Automatic retries in the HTTP client are disabled.
- **Series exist from the start.** GMP treats a counter's first scraped value as its starting point and drops everything counted before it. The tester exports every expected series with a zero value before the first request so that nothing is lost.

## Protocol

Run by `run.sh`.

- **Ramp:** 5k to 100k RPS per framework in 5k steps, 30 s per step (20 stages, 10 minutes). Each tester pod stays at or below 20k RPS.
- **Pairs:** two frameworks run at the same time, one per app node. Their testers share the clients node, which has enough headroom (see Validation).
- **Scenarios:** `GET /api/devices` then `POST /api/devices` for each pair.
- **Repetitions:** 3. The framework order, and therefore the pairs and the node each framework lands on, is shuffled in every repetition. `runs.csv` records the node.
- **SLO for "max rate":** p99 ≤ 50 ms, achieved ≥ 95% of the target rate, and errors (non-2xx, timeouts and dropped requests) ≤ 1% of the target rate.

## Metric definitions

| Metric | Definition |
|---|---|
| Achieved RPS | 2xx responses per second. |
| Target (scheduled) RPS | The rate the tester's schedule sends. |
| Errors | Non-2xx responses, timeouts and dropped requests per second. |
| Availability | 2xx responses within the 1 s deadline, divided by scheduled requests. |
| p50/p90/p99 | Latency percentiles of all sent requests, from the scheduled send time. |
| App CPU | cAdvisor `container_cpu_usage_seconds_total`. `analyze.py` interpolates the counter over a 150 s window centred on each stage, accurate to about ±0.1 core. |
| CPU throttling | Throttled CFS periods divided by all CFS periods. It is 0 until the app hits its 2-CPU quota. |

## Running

```bash
cd benchmark/go-frameworks

# Build images (Cloud Build; no local Docker needed)
env -u CLOUDSDK_AUTH_ACCESS_TOKEN gcloud builds submit app --config app/cloudbuild.yaml --region us-central1
env -u CLOUDSDK_AUTH_ACCESS_TOKEN gcloud builds submit loadtester --tag us-central1-docker.pkg.dev/go-bench-15205/bench/loadtester:v3 --region us-central1

# Full run (about 4.5 hours), then analysis and validation
gke/run.sh                      # writes results/gke-<run id>/runs.csv
gke/analyze.py results/gke-<run id>
gke/validate.py results/gke-<run id> > results/gke-<run id>/validation.txt

# Short smoke run into overload
REPS=1 FRAMEWORKS="stdlib fiber" SCENARIOS=get STAGES=4 START_RPS=4000 STEP_RPS=6000 gke/run.sh smoke
```

`run.sh` settings are environment variables: `REPS`, `FRAMEWORKS`, `SCENARIOS`, `PODS`, `START_RPS`, `STEP_RPS`, `STAGES`, `STAGE_S`, `DEADLINE_MS` and `IMAGE_TAG`.

## Validation

`validate.py` compares the tester's numbers with independent sources:

1. **Accounting over each whole run.** Completed plus dropped requests must equal the exact number of scheduled requests. The script recomputes the schedule with the same integer arithmetic as the tester.
2. **Requests vs. packets.** Each request and each response fits in one TCP packet, so the packets received by the app pod's network interface (kernel counters via cAdvisor) are an independent count of the requests that reached the app. The ratio must be about 1.00.
3. **CPU.** cAdvisor must agree with GKE system metrics (`kubernetes_io:container_cpu_core_usage_time`), and both must stay within the 2-core CFS quota.
4. **Load generator headroom.** The busiest tester pod's CPU must stay below its 1-CPU limit.

The first GKE run (`results/gke-20260925-003821`) was analysed this way. Its `validation.md` records the problems found, which led to the current tester and scripts.

## Dashboard

The Grafana dashboard ("Go frameworks benchmark (GKE)") shows only data from tester v3 runs (series with a `run` label). Each panel title states what the reader needs to know:

- **p99 latency:** the dashed line is the 50 ms SLO.
- **Requests per second:** the solid line is 2xx responses and the dashed line is the target. A gap between them means the app is saturated.
- **CPU usage:** a 3-minute average, accurate to about ±5%. cAdvisor sample timestamps lag the real measurement by 10–15 s, so shorter windows read above 100%, which the CFS quota makes impossible.
- **Memory usage:** working set as % of the 256 MiB limit.
- **Availability:** 2xx within 1 s, as % of scheduled requests.
- **CPU throttling:** the exact saturation signal.

## Known limitations

- Results describe a 2-CPU container with a trivial handler (JSON encode/decode, no database). They show per-request framework overhead, not the behavior of an I/O-bound application.
- The resolution of "max rate within SLO" is one ramp step (5k RPS). A difference of one step between frameworks is within run-to-run noise unless all repetitions agree.
- Latency above saturation reflects the tester's bounded backlog (up to the 1 s deadline), which is what a user with a 1 s timeout would see. It does not measure the server's own service time.
- Only HTTP/1.1 is tested.
